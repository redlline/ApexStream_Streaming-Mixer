# ApexStream — Streaming Mixer

Вставка рекламы и графики в живые потоки **без разрыва эфира у зрителя**.

Система принимает поток от провайдера, накладывает на него баннеры, логотип,
HTML-графику, полноэкранные ролики и живую врезку из OBS — и отдаёт результат
во Flussonic и/или напрямую зрителям. Слои добавляются и снимаются на лету,
publish при этом не прерывается.

Управление — через веб-панель или REST API (можно повесить на аппаратный пульт
вроде Bitfocus Companion).

## Что умеет

**Эфир**
- Баннеры GIF/PNG с плавным появлением — в баннерной зоне или в произвольном
  месте кадра (перетаскиванием прямо на превью).
- HTML-шаблоны — живая графика из браузера (таймеры, таблицы, бегущие строки)
  с библиотекой заготовок и предпросмотром.
- Полноэкранные MP4-ролики со звуком и автоматической нормализацией громкости.
- Постоянный логотип канала — запоминается **отдельно для каждого источника**.
- Живая врезка из OBS поверх эфира: сначала предпросмотр, потом выход в эфир.

**Источники**
- HTTP/HLS, RTSP, SRT — забираем сами.
- SRT-push — внешний энкодер (Astra Cesbo и т.п.) пушит нам, слушаем мы:
  через MediaMTX или напрямую движком, если MediaMTX не справляется с потоком.
- YouTube-трансляции — через релей, который сам переполучает ссылку.
- Пресеты входов: переключение источника на лету, без разрыва выхода.
- Автопереход на резервный источник, если основной замолчал.
- Выбор аудиодорожки для эфира — своей для каждого источника.
- Мультиязык: несколько аудиодорожек одновременно.

**Устойчивость**
- Встроенный буфер: короткий провал провайдера зритель не замечает.
- Заглушка на длинных обрывах вместо чёрного экрана.
- Выходной конвейер не останавливается, даже когда вход полностью пропал.

**Управление**
- Веб-панель: мультивью, превью эфира, VU-метры, расписания, очередь,
  операторская программа-напоминалка.
- Три роли: `viewer` (только смотрит), `operator` (управляет эфиром),
  `admin` (плюс пользователи и серверы).
- Разграничение потоков: оператор видит и трогает только свои, админ — все,
  видит владельца и может передать поток другому оператору.
- Счётчик подключений: видно, забирает ли кто-то выход потока прямо сейчас.
- Журнал действий с поиском, очистка журнала, сессий и логов.
- Одна панель на несколько серверов с переключением.
- REST API для пультов и автоматизации — см. [docs/API.md](docs/API.md).

## Архитектура

```
источник ──► gst_streamg.py (один процесс на поток) ──┬──► RTMP publish ──► Flussonic ──► зрители
                                                       └──► MediaMTX ──► HLS / RTSP / SRT / WebRTC
```

Внутри процесса — два GStreamer-конвейера, связанных `intervideo`/`interaudio`:

- **P1 (вход)** — `uridecodebin` → нормализация (масштаб, fps, формат) →
  очередь-задержка (буфер). Может падать и переподключаться сколько угодно:
  нестабильный провайдер — это норма.
- **P2 (выход)** — стартует один раз и живёт до команды «Стоп».
  `intervideosrc` (при голодании повторяет последний кадр, поэтому publish
  **не рвётся никогда**) → `compositor` → `nvh264enc` (GPU) → publish.

Слои компоновщика, снизу вверх:

| Слой | Что это |
|---|---|
| 1 | эфир (или заглушка при обрыве) |
| 2 | OBS-врезка |
| 3 | баннер |
| 4 | логотип |
| 5 | HTML-графика |
| 9 | полноэкранный ролик |

Порядок фиксирован, поэтому баннер и логотип видны **поверх** OBS-врезки, а
ролик перекрывает всё.

**Нагрузка.** Видео кодируется один раз, на GPU (NVENC). CPU занят только
декодированием входа, наложением слоёв и звуком. HTML-графика — отдельный
процесс Chromium, живёт только пока графика на экране.

## Состав

| Компонент | Где живёт | Порт | Назначение |
|---|---|---|---|
| **Агент** | сервер с GPU (рядом с Flussonic) | 8500 | микширование, API, медиатека |

Агентов может быть несколько — панель одна, сверху переключатель серверов.

```

ui/
  server.py           — панель: авторизация, роли, прокси к агентам

deploy/
  ad-agent.service, ad-ui.service — юниты systemd
  yt-relay.sh                     — релей YouTube → MediaMTX

docs/
  Руководство-оператора.html — как работать в панели (для операторов)
  API.md                     — справочник REST API
```

## Требования

**Сервер агента**
- Ubuntu 22.04 / 24.04
- NVIDIA GPU с NVENC и драйвером (проверка: `nvidia-smi`)
- GStreamer 1.20+ с плагинами `good`, `bad`, `ugly`, `libav`, `nvcodec`, `srt`
- Python 3.10+ и `python3-gi` (системный пакет, **не** через pip)
- ffmpeg с NVENC и libsrt

**Сервер панели** — Python 3.10+, больше ничего.

## Установка

### Агент

```bash
apt update && apt install -y python3-venv python3-gi python3-gi-cairo \
  gir1.2-gstreamer-1.0 gstreamer1.0-plugins-{good,bad,ugly} \
  gstreamer1.0-libav gstreamer1.0-nvcodec ffmpeg

useradd -r -s /usr/sbin/nologin adstreamer
mkdir -p /opt/ad-streamer && cd /opt/ad-streamer
# положите сюда каталог agent/

python3 -m venv venv
./venv/bin/pip install -r agent/requirements.txt
./venv/bin/playwright install chromium
./venv/bin/playwright install-deps
```

Файл `/opt/ad-streamer/agent.env` (права `600`):

```ini
API_KEY=сгенерируйте_длинный_случайный_ключ
DATA_DIR=/opt/ad-streamer/data
FFMPEG=ffmpeg
TZ=Asia/Ashgabat
```

Ключ удобно сгенерировать: `openssl rand -hex 24`

```bash
mkdir -p /opt/ad-streamer/data
chown -R adstreamer:adstreamer /opt/ad-streamer
cp deploy/ad-agent.service /etc/systemd/system/
systemctl daemon-reload && systemctl enable --now ad-agent
systemctl status ad-agent
```

**MediaMTX** нужен для OBS-врезки, приёма SRT-push и отдачи зрителям. Скачайте
релиз в `/opt/ad-streamer/mediamtx/`, положите рядом `mediamtx.yml`. Агент
запускает его и следит за ним сам — отдельный юнит systemd не нужен. Ключевое
в конфиге:

```yaml
srt: yes
srtAddress: :8890
paths:
  all_others:
```

### Панель

```bash
cd /opt/ad-streamer
python3 -m venv venv-ui
./venv-ui/bin/pip install -r ui/requirements.txt
```

Файл `/opt/ad-streamer/ui.env` (права `600`):

```ini
ADMIN_PASSWORD=надёжный_пароль_администратора
AGENT_URL=http://IP_АГЕНТА:8500
API_KEY=тот_же_ключ_что_у_агента
UI_DATA=/opt/ad-streamer/ui-data
HLS_UPSTREAM=http://IP_АГЕНТА:8080
TZ=Asia/Ashgabat
```

```bash
mkdir -p /opt/ad-streamer/ui-data
cp deploy/ad-ui.service /etc/systemd/system/
systemctl daemon-reload && systemctl enable --now ad-ui
```

Панель откроется на `http://IP:8080`, логин `admin`.

> Если `ADMIN_PASSWORD` не задан, при первом запуске генерируется случайный
> пароль и пишется в журнал (`journalctl -u ad-ui`). Пары `admin/admin`
> система не создаёт намеренно.

Наружу публикуйте **только панель и только по HTTPS** (nginx + сертификат).
Порт агента 8500 держите в локальной сети или за VPN.

> **Часовой пояс.** `TZ` в env-файлах задавайте явно. Процесс кеширует зону при
> старте: если запустить службу, когда система ещё в UTC, а зону сменить позже,
> расписания останутся в старой зоне. После смены `TZ` службу нужно
> перезапустить.

## Работа с панелью

> Для операторов есть отдельный документ — **[docs/Руководство-оператора.html](docs/Руководство-оператора.html)**:
> пошагово, без технических подробностей, готов к печати в PDF

> Ниже — краткий обзор тех же возможностей.

### Создание потока

Вкладка **Потоки** → «Добавить поток».

| Поле | Пояснение |
|---|---|
| название | как будет видно в списке |
| тип входа | «забираем сами», «нам пушат по SRT» или «YouTube-трансляция» |
| входящий | URL источника (для режима pull) |
| streamid | имя канала (для режима push) |
| ссылка на YouTube | адрес трансляции (для режима YouTube) |
| исходящий | RTMP publish во Flussonic; можно оставить пустым |
| кадр Ш×В | разрешение выхода |
| баннер Ш×В | размер баннерной зоны |
| кодек / битрейт | `h264_nvenc` (GPU) или `libx264` (CPU) |
| автостарт | поднимать ли поток при старте агента |
| аудиодорожки | **первый номер уходит в эфир**; несколько через запятую — мультиязык |
| заглушка при обрыве | картинка вместо чёрного экрана, когда провайдер молчит |

Поток принадлежит тому, кто его создал: другие операторы его не видят, админ
видит все потоки с именем владельца.

Ссылку на YouTube можно вставить прямо в поле «входящий» — панель распознает
её и переключит тип входа сама.

Если «исходящий» пустой, а MediaMTX включён — поток раздаётся напрямую
(HLS/RTSP/SRT/WebRTC), ссылки появятся у потока после старта.

### Приём потока от Astra Cesbo и других энкодеров

Когда источник умеет только SRT-caller, он пушит нам, а слушаем мы. Это как раз
случай, когда сеть источника видит нас, а мы её — нет.

1. В форме добавления потока выберите **«нам пушат по SRT»**.
2. Впишите `streamid` — любое имя латиницей, например `astra1`.
3. Панель покажет готовую строку — скопируйте её в энкодер:
   `srt://IP_АГЕНТА:8890?streamid=publish:astra1`
4. Вход потока подставится автоматически:
   `rtsp://127.0.0.1:8554/astra1`

Приёмник заранее настраивать не нужно — путь создаётся автоматически по вашему
`streamid`. Один порт обслуживает сколько угодно источников, они различаются по
`streamid`. Допустимы латиница, цифры, дефис и подчёркивание.

Энкодер отдаёт по **SRT**, а микшер забирает по **RTSP** — так сделано
намеренно. SRT-выход MediaMTX отдаёт не всякий кодек: вещательный MPEG-2
(обычное дело для Astra и аппаратных энкодеров) через него не читается, хотя
путь заводится и числится готовым. По RTSP такой поток идёт нормально, H.264
тоже.

**Сначала запустите энкодер, потом жмите «Старт».** Перед запуском агент
проверяет вход, и если энкодер ещё не пушит, старт будет отклонён с ошибкой
`Input/output error` — это ожидаемо, а не поломка.

Убедиться, что энкодер достучался, можно так:

```bash
curl -s http://127.0.0.1:9997/v3/paths/list | python3 -m json.tool
```

Путь должен быть в списке с `"ready": true`, а в `tracks` будут видны кодеки
источника.

> Некоторые энкодеры (в том числе Astra Cesbo) принимают параметры SRT через
> `#`, а не `?`, и понимают стандартный синтаксис streamid:
> `srt://IP:8890#streamid=%23!::r=astra1,m=publish`. Оба варианта дают тот же
> результат — путь `astra1`.

#### Если через MediaMTX видео не доходит

Бывают источники, которые MediaMTX принимает, но разобрать не может. На
спутниковом канале через Astra он принимал все 7.5 Мбит/с, а в путь клал
только звук: видео молча выбрасывал, не сумев разобрать параметры H264
(`width=0, height=0` у трека). Измерено на живом канале — SRT-соединение
показывало 7.49 Мбит/с приёма, а путь прирастал на 0.69 Мбит/с.

Для таких источников есть второй способ приёма — **напрямую движком**: он
слушает собственный порт, MediaMTX не участвует. GStreamer разбирает
MPEG-TS сам и к подобным потокам не придирается.

1. В форме выберите тип входа «нам пушат по SRT», способ приёма —
   **«напрямую движком»**.
2. После создания панель покажет готовый адрес: `srt://IP_АГЕНТА:170NN`,
   где `NN` — номер потока.
3. В энкодере укажите этот адрес, режим **caller**, `Stream ID` —
   **оставьте пустым**: здесь различает порт, а не имя.

У каждого потока свой порт, `17000 + номер потока`. Несколько каналов
работают одновременно, каждый на своём порту.

| | через MediaMTX | напрямую движком |
|---|---|---|
| Порт | один общий (8890) | свой на каждый поток |
| Различает | `streamid` | порт |
| Просмотр источника до эфира | есть | нет |
| Капризные источники | не всегда | принимает |

Что теряется при прямом приёме: исходный сигнал читает только движок,
поэтому нельзя смотреть его отдельно от эфира. **Выход не затронут** —
раздача через MediaMTX, ссылки и Flussonic работают как обычно, зрителей
сколько угодно.

Состав аудиодорожек при прямом приёме показывает сам движок — внешний
`ffprobe` к занятому порту подключиться не может. Кнопка «🎚 Дорожки»
работает как обычно, но только когда поток запущен и энкодер подключён.

> Порт зависит от номера потока, а номера после удаления могут
> переиспользоваться. Не пересоздавайте потоки без нужды — правьте
> существующие; иначе порт достанется другому каналу и придётся править
> настройки энкодера.

Адрес в подсказке берётся из карточки сервера, поэтому при добавлении новых
серверов править ничего не нужно. Если энкодер должен пушить по другому адресу,
чем тот, по которому панель видит агента (отдельный интерфейс, NAT), задайте
его явно в настройках сервера.

### Кто забирает выход

Рядом со статусом «В ЭФИРЕ» появляется метка **👁 N** — сколько потребителей
прямо сейчас читают выход потока (HLS, RTSP, SRT, WebRTC); в подсказке разбивка
по протоколам. Это ответ на вопрос «мой выход вообще кто-то тянет?».

> Считаются **подключения к микшеру, а не зрители**. Flussonic забирает поток
> одним подключением, за которым может стоять сколько угодно людей — их считает
> уже он сам (`/streamer/api/v3/sessions`, поле `estimated_count`).

Данные берутся у MediaMTX и кэшируются на пару секунд: список потоков панель
опрашивает часто, и ходить в API на каждый поток отдельно было бы расточительно.

### Показ баннера, HTML и роликов

У запущенного потока: **Баннер**, **HTML**, **Ролик**.

- **Длительность** — сколько держать на экране, считая время появления.
- **Fade** — плавность появления и исчезновения.
- **Ручное размещение** — если открыто превью эфира, рамку можно перетащить
  прямо на картинке и задать точное место и размер.

Ролик идёт поверх всего и снимается кнопкой «Снять ролик». Баннер, HTML и
логотип видны поверх обычного эфира и поверх OBS-врезки.

Баннеры разных размеров на одном потоке вписываются в баннерную зону с
сохранением пропорций и прижимаются к нижней кромке по центру. Чтобы
«квадратные» баннеры показывались крупно, задайте зону по самому высокому из
них (например `1920×360`) — бегущая строка всё равно останется внизу.

### Логотип

«Логотип» у потока: выберите картинку и место. При включённом превью логотип
можно перетащить мышкой и задать точный размер.

Настройка запоминается **для каждого пресета входа отдельно**: переключились на
другой источник — логотип принял вид, настроенный для него.

### OBS-наложение

Живая картинка из OBS поверх эфира, в два шага — чтобы не выпустить в эфир
непроверенный сигнал.

1. В OBS: «Настройки → Вещание → Пользовательский», сервер
   `srt://IP_АГЕНТА:8890?streamid=publish:obs1`, режим caller.
2. В панели **«Включить»** — сигнал появляется в превью карточки, в эфире пока
   ничего не меняется.
3. **«В эфир»** — картинка плавно выходит в эфир.
4. **«Стоп»** — плавно снимается, канал отключается.

Режим звука:

| Режим | Что слышно |
|---|---|
| «глушить эфир» | **только** звук OBS |
| «оставить звук эфира» | **только** звук эфира (видео без звука OBS) |

Если с OBS не идёт **ничего**, кнопка «В эфир» не сработает — иначе она
заглушила бы трансляцию, не показав и не дав ничего взамен. Сигналом считается
любое из двух: картинка или звук. Поэтому заставка, статичный кадр и видео на
паузе (звука нет) проходят так же, как и одна музыка без картинки.

### Пресеты входов

«Входы» у потока — сохранённые источники. Переключение идёт **без разрыва**
выхода: publish не прерывается, зритель ничего не замечает.

Текущий вход, если он не был сохранён, автоматически сохраняется как «Прежний
вход» — вернуться можно одним кликом. У каждого пресета видна полная ссылка с
кнопкой «Скопировать путь».

Галочка «автопереключение» — переход на следующий пресет, если текущий источник
замолчал.

**Аудиодорожки запоминаются для каждого входа отдельно.** Кнопка «🎚 Дорожки» у
пресета показывает реальный состав источника с языками — выбираете, какая идёт
в эфир. Это важно: провайдеры часто ставят первой служебную дорожку (интершум,
чистый звук со стадиона), а речь — второй, и у разных источников порядок разный.

Без этой настройки после переключения входа в эфир уходила тишина: движок искал
дорожку с прежним номером, у нового источника её не оказывалось, и вместо неё
подставлялась тишина (иначе конвейер завис бы, ожидая данные с несуществующей
дорожки, и пропало бы всё, включая видео).

Смена порядка при том же количестве дорожек применяется на лету. Смена
количества требует перезапуска потока — оно определяет структуру выходной части
(сколько каналов слушает микшер и сколько дорожек уходит в мультиязычный SRT).
Агент делает такой перезапуск сам и пишет причину в журнал.

### Источник YouTube

Выберите тип входа **«YouTube-трансляция»** и вставьте ссылку — лучше в форме
`https://www.youtube.com/@КАНАЛ/live`: она всегда указывает на текущую
трансляцию канала, тогда как `watch?v=…` привязана к конкретному эфиру и
умрёт вместе с ним.

YouTube не отдаёт постоянный адрес потока: ссылка живёт около 6 часов. Поэтому
между YouTube и микшером работает **релей** — отдельный процесс, который сам
переполучает ссылку. Он запускается вместе с потоком, гаснет вместе с ним и
поднимается заново, если упал; следить за ним не нужно.

Трансляция должна идти в момент старта — иначе старт будет отклонён с
сообщением об отсутствии сигнала.

> Извлечение опирается на `yt-dlp`, а YouTube ломает его несколько раз в год.
> Обновление поставлено на расписание (см. «Обслуживание»). Если поток
> перестал стартовать, а в журнале `No video formats found` — обновите
> вручную: `systemctl start yt-dlp-update`.

### Проверка входа

Вкладка **Проверка** — посмотреть источник до того, как заводить из него поток.
Вставьте URL, нажмите «Проверить» — сервер запустит короткую пробу и покажет
картинку.

> Проба показывает **то, что реально приходит**. Чёрный экран и тишина
> означают, что источник действительно отдаёт пустой сигнал. Для событийных
> каналов между трансляциями это нормально и неисправностью не является.

### Расписания, очередь, программа

- **Очередь** — список баннеров по кругу, для показа по расписанию.
- **Расписание** — показ в заданное время, с повтором каждые N минут и
  диапазоном дат.
- **Программа** — сценарий эфира с напоминаниями оператору. Сама она ничего в
  эфир не выпускает, только подсказывает, что и когда пора запустить.

### Пользователи и разграничение потоков

Вкладка **Пользователи** (видна админам): создание учётных записей, смена роли
и пароля, статистика работы в панели и журнал действий.

| Роль | Что может |
|---|---|
| `viewer` | только смотреть, изменить ничего не может |
| `operator` | управляет эфиром — но **только своими потоками** |
| `admin` | всё, включая чужие потоки, пользователей и серверы |

**Поток принадлежит тому, кто его создал.** Другие операторы его не видят и не
могут ни запустить, ни остановить, ни изменить — так операторы не мешают друг
другу. Админ видит все потоки и колонку «Создал»: если что-то сломано, видно,
чей это поток.

Потоки, созданные до появления разграничения (или напрямую через API), не имеют
владельца и доступны всем — иначе люди разом потеряли бы доступ к тому, с чем
уже работают.

**Передача потока.** Админ может отдать поток любому оператору — кнопка
«Назначить» в колонке «Создал». После этого оператор работает с ним как со
своим, включая удаление: раз поток на нём, он должен уметь и убрать его, не
дёргая администратора. У переданных потоков стоит метка «назначен», так что
видно, где решение админа, а где работа самого оператора. Пустой выбор снимает
владельца — поток становится общим.

Забрать чужой поток себе оператор не может: передаёт только админ.

> Это защита от случайной порчи чужой работы, а не от злоумышленника. У кого
> есть API-ключ агента, тот обращается к нему напрямую и видит все потоки —
> иначе перестали бы работать пульты и скрипты. Ключ держите в секрете.

**Журнал действий** — кто и что делал, с поиском по логину, действию и дате.
Поиск идёт по всей базе (до 2000 записей), а не только по показанным строкам.

Кнопки очистки: журнала действий (само удаление тоже записывается — остаётся
след, кто чистил), чужих сессий (разлогинивает всех, кроме вас — пригодится,
если чей-то ноутбук остался открытым) и логов агента на вкладке «Логи».

## API

Полный справочник: **[docs/API.md](docs/API.md)** — все эндпоинты, параметры,
готовые примеры `curl` и раздел про подключение аппаратного пульта.

Коротко:

```bash
KEY="ваш_ключ"; A="http://IP_АГЕНТА:8500"

curl -s $A/api/streams -H "X-API-Key: $KEY"                    # что в эфире
curl -s -X POST $A/api/streams/1/start -H "X-API-Key: $KEY"    # запустить
curl -s -X POST $A/api/streams/1/play  -H "X-API-Key: $KEY" \
     -F banner_id=5 -F duration=15                             # показать баннер
```

Пульты (Bitfocus Companion, Touch Portal) подключаются обычными HTTP-запросами
и работают напрямую с агентом — даже если панель недоступна.

## Несколько серверов

Панель работает с любым количеством агентов. Вкладка **Настройки** → «Серверы»:
название, адрес агента, его API-ключ и HLS-адрес для встроенного плеера. Кнопка
«Проверить» покажет, есть ли связь. Переключатель появляется в шапке, когда
серверов больше одного.

У каждого агента своя база и своя медиатека — они независимы.

### Синхронизация потоков

Один и тот же поток не нужно набивать руками на каждом сервере.

- **При создании** — галочка «создать и на других серверах» и список серверов
  с отметками. Появляется, когда серверов больше одного.
- **Кнопка «⇄ Синхронизировать сейчас»** в шапке карточки «Потоки» —
  разложит на выбранные серверы все уже существующие потоки со всеми
  настройками.
- **При удалении** панель спросит, удалить ли одноимённый поток и на других
  серверах, или только на текущем.

Копируется всё: кадр, кодек, вход, выход во Flussonic, аудиодорожки, логотип
с его координатами, буфер и заглушка. Картинки логотипа и заглушки
переносятся в медиатеку целевого сервера физически — одноимённые не
дублируются. Потоки сопоставляются по названию, одноимённый обновляется.

> **Копия создаётся остановленной, и автостарт у неё выключен.** Иначе два
> сервера сразу начали бы публиковать в один адрес Flussonic и рвали бы эфир
> друг другу. Запускать копию — ваше решение.

> При обновлении кода агента раскладывайте его **на все серверы сразу**, иначе
> они разъедутся по возможностям.

## Обслуживание

### Обновление

```bash
# бэкап
cp /opt/ad-streamer/agent/main.py /root/backup_$(date +%F_%H%M).py

# выложить новый файл и проверить синтаксис
python3 -m py_compile /opt/ad-streamer/agent/main.py

systemctl restart ad-agent
```

> **Важно.** Перезапуск `ad-agent` может убить движки живых потоков — поведение
> зависит от того, как systemd обойдётся с группой процессов, и не является
> предсказуемым. **После каждого перезапуска проверяйте, что потоки в эфире**,
> и при необходимости поднимайте вручную:
>
> ```bash
> curl -s $A/api/streams -H "X-API-Key: $KEY"                 # смотрим status.running
> curl -s -X POST $A/api/streams/1/start -H "X-API-Key: $KEY"
> ```
>
> Файлы панели (`static/index.html`) отдаются с диска — для них перезапуск не
> нужен, достаточно обновить страницу в браузере.

Движок (`gst_streamg.py`) запускается заново на каждый поток, поэтому его новая
версия подхватывается при следующем старте потока — перезапускать `ad-agent`
ради неё не нужно.

### Обновление yt-dlp (источники YouTube)

YouTube ломает извлечение потоков несколько раз в год. Держать это на памяти
оператора ненадёжно: узнаёшь о проблеме в тот момент, когда эфир уже не
поднялся. Поэтому обновление стоит на расписании:

```bash
systemctl status yt-dlp-update.timer    # раз в неделю, ночь понедельника
journalctl -u yt-dlp-update             # история обновлений
systemctl start yt-dlp-update           # обновить немедленно
```

Признак, что пора обновить вручную: поток с YouTube не стартует, а в журнале
`No video formats found` или `Precondition check failed`.

Юниты ставятся один раз:

```bash
cp deploy/yt-dlp-update.{service,timer} /etc/systemd/system/
cp deploy/yt-relay.sh /usr/local/bin/ && chmod +x /usr/local/bin/yt-relay.sh
systemctl daemon-reload && systemctl enable --now yt-dlp-update.timer
```

### Диагностика

```bash
systemctl status ad-agent
journalctl -u ad-agent -f
curl -s "$A/api/logs?stream_id=1" -H "X-API-Key: $KEY"   # журнал движка
nvidia-smi                                                # GPU и сессии NVENC
```

Число сессий NVENC складывается из наших потоков **и** транскодеров Flussonic
на том же сервере: три ABR-профиля по четыре рендиции — это уже 12 сессий ещё
до нашего единственного энкода.

### Типичные ситуации

| Симптом | Причина и что делать |
|---|---|
| Проба показывает чёрный экран | источник действительно пустой — вопрос к провайдеру |
| Поток «отваливается» у зрителя после паузы | во Flussonic он объявлен как `ondemand` — замените на `stream` |
| Не подключается SRT-источник | проверьте формат: одни отдают через `?streamid=`, другие через путь `/read:имя` |
| OBS-врезка не выходит в эфир | с OBS не идёт ни картинки, ни звука — проверьте, что вещание запущено |
| Замена картинки не видна | GIF/HTML вступают в силу со следующего показа; логотип меняется на лету |
| После переключения входа пропал звук | у нового источника другой порядок дорожек — задайте их для этого входа кнопкой «🎚 Дорожки» |
| Поток с YouTube не стартует | трансляция не идёт, либо устарел `yt-dlp` — `systemctl start yt-dlp-update` |
| Оператор не видит поток | поток создан другим оператором; полный список — у админа, он же может передать поток кнопкой «Назначить» |
| Astra подключается, но видео нет | MediaMTX не смог разобрать поток — переведите вход на приём «напрямую движком» |
| «Address already in use» при опросе дорожек | у прямого приёма порт занят движком; состав дорожек он отдаёт сам, но только пока поток запущен |
| Метка 👁 показывает 1, а зрителей много | это подключения к микшеру: за одним подключением Flussonic стоят все его зрители |
| Транскодер держит сессии NVENC при простое | это Flussonic: поток объявлен как `stream`, транскодер работает и без зрителей. Нужен `ondemand` |

### Откат

```bash
systemctl disable --now ad-agent ad-ui
rm -rf /opt/ad-streamer
userdel adstreamer      # если пользователь больше не нужен
```

Системный Python и Flussonic при установке не затрагиваются, всё изолировано в
`/opt/ad-streamer`. Базы — файлы SQLite, отдельных демонов нет.

## Безопасность

- API-ключ агента даёт **полный контроль над эфиром**. Порт 8500 — только в
  локальной сети или за VPN.
- Наружу — только панель, только по HTTPS.
- Сервисы работают от системного пользователя `adstreamer` (nologin), не от
  root. Секреты — в `agent.env` / `ui.env` с правами `600`.
- Роли: `viewer` не меняет ничего, `operator` управляет эфиром, `admin`
  дополнительно управляет пользователями и серверами.
- Потоки разграничены между операторами: логин и роль панель передаёт агенту
  из серверной сессии, подделать их с клиента нельзя. Проверка доступа стоит
  одним заслоном на всех адресах вида `/api/streams/<id>/…`, а не в каждом
  эндпоинте по отдельности — так её нельзя забыть в новом.
- Сессии имеют срок жизни и таймаут простоя, cookie помечена `Secure`.
  Админ может завершить чужие сессии одной кнопкой.
- Действия пишутся в журнал аудита с указанием пользователя и сервера;
  очистка журнала тоже фиксируется.
- Control-сокеты движка и порт HTML-скринкаста слушают только `127.0.0.1`.
- В репозитории нет ключей и паролей: всё берётся из env-файлов, которые
  исключены через `.gitignore`.
